# 直接用一句话查看聊天

可以直接对接入此 MCP 的助手说“看一下我和 Alex 的聊天记录”，不用记工具名、微信 ID 或 QQ UID。助手需要把这句话落实为明确的会话、平台和读取范围，再调用工具。当前对话已经确定的人、群和日期可以沿用；只有仍影响结果的歧义需要补充说明，不要求每次重新确认。

下面的姓名、群名、号码和日期都是示例。本文说明自然语言请求应怎样处理；不是一个把任意中文自动解析成查询的独立程序，也不代表已经验证所有客户端模型都会正确选择工具。

## 怎样说，怎样读

| 用户的说法 | 应采用的读取范围 | 什么情况下需要先澄清 |
| --- | --- | --- |
| “看一下我和 Alex 的聊天记录” | 先查候选，结合当前对话确定目标。未指定日期时说明实际采用的范围；如果只是先读最近内容，要明确这是最近部分。 | 同名候选无法区分；微信与 QQ 的目标无法确定；任务需要完整覆盖但时间含义不清。不是缺一个可选参数就必须问一次。 |
| “只看微信里 Alex 的聊天” | 只解析和读取微信目标，沿用已明确的日期范围。 | 微信里有多个无法区分的同名候选。QQ 是否配置不应阻止这次微信读取。 |
| “看看 QQ 群‘项目讨论’昨天的聊天” | 查 QQ 群候选，使用群 ID 和群聊类型；昨天按当前日期与明确时区换算。 | 同名群无法区分；当前对话使用的时区不明确且会影响日期。不能默认为 QQ 私聊。 |
| “看看微信群‘项目讨论’昨天的聊天” | 只找微信群候选，然后读取该群昨天的记录。 | 同名群仍有歧义。群名相同的联系人不是这个目标。 |
| “微信和 QQ 都看看 Alex 的消息” | 分别确定两边账号，保留平台来源后合并阅读。 | 无法确认两边是不是用户所指的那个人。相同昵称本身不是跨平台身份依据。 |
| “把 2026 年 10 月 9 日那天从头到尾看完” | 目标会话在 +08:00 的这个自然日，按时间顺序逐页读到终点。 | 目标会话尚未确定，或用户明确采用了其他时区。单日范围不应扩成前后几天。 |
| “看看最近几天” | 先利用当前对话已经说清的日期；仍模糊时说明所采用的具体起止时间。 | 几天的差别会改变统计、比较或完整阅读结论。没有固定“近 7 天”规则。 |
| “最近 50 条给我看一下” | 明确目标后取最近 50 条；可以按聊天顺序展示这批记录。 | 目标会话仍有歧义。50 条是本次请求范围，不能称为全部历史。 |
| “这个人的全部聊天都看，别漏” | 所选平台、所选会话的全部本机可读历史，逐页读取并记录覆盖范围；可分段处理。 | “全部”是否还包括另一个平台确实不明。不能把“全部”自行改成最近 100 条或最近几天。 |
| “找一下他说‘周五交’的那句话，再看看前后” | 在目标会话内搜索，使用命中的记录身份展开前后文。 | 有多处命中且无法判断指哪一处；“他”没有明确指代。不能把关键词命中列表当成完整对话。 |
| “这个群上周谁说得最多” | 确定群与上周的具体日期，读取群统计，按稳定发送者 ID 计数。 | 群不明确，或“上周”采用的周范围与当前对话冲突。部分扫描不能当全群计数。 |
| “只看这条语音 / 图片 / 表情” | 从当前会话的准确消息取得对应媒体，再读取转写或图片预览；必要时补充这条消息的前后文。 | “这条”没有可定位的消息，或相同原生消息号对应多个本地记录。不能任选附近的媒体代替。 |

候选的排序、最近活跃程度或第一条结果都不等于身份已经唯一。已有可靠的会话 ID 可以直接复用；存在多个候选时，可用用户给出的备注、群名、账号或上下文缩小范围。仍无法区分时，只问能解决歧义的信息。某个平台出错或候选被截断，也不能因此宣称另一个结果就是唯一目标。

0.3.2的统一解析工具支持明确平台：`unified_resolve_chat(query="Alex", source="wechat")`只查询微信；`source="qq"`只查询QQ；省略时仍查询两者。微信群增加`wechat_type_filter="group"`，QQ群增加`qq_chat_type="group"`。这样未使用的平台缺少配置或暂不可用，不会阻止明确的单平台需求。

## 日期、全部和分页

“今天”“昨天”“上周”需要先落实到当次请求的具体日期。统一工具的 `date=YYYY-MM-DD` 表示 +08:00 自然日，不能同时传 `after` 或 `before`。单日阅读优先用 `date`，例如：

```json
{
  "wechat_chat": "wxid_example",
  "date": "2026-10-09",
  "order": "asc"
}
```

以上是 `unified_timeline` 的参数示例，示例 ID 需要换成已解析的目标。精确到时分秒的范围可使用带时区的时间：`after="2026-10-09T14:00:00+08:00"`、`before="2026-10-09T18:00:00+08:00"`，表示从 14:00 起、到 18:00 前。

统一 MCP 工具的纯日期 `before="2026-10-09"` 会包含 10 月 9 日整天。它与 [导出工作流](WORKFLOW.md) CLI 的截止日期语义不同：CLI 将纯日期解释为当天零点，并使用左闭右开范围。不要把两个入口的日期参数原样互换。

不要用空字符串表示“未指定日期”，应省略参数；不要把`20261009`直接作为时间参数，它会因歧义被拒绝，改用`2026-10-09`。开始时间晚于截止时间会报错，不会假装完整读出了零条。

统一时间线默认每页 100 条，最多 500 条，这是页大小。要完成用户指定的整天、完整日期范围或全部历史，继续传回 `next_cursor`，保持原会话与筛选条件，直到明确的 `has_more=false`。微信和 QQ 原生工具的分页字段见 [工具说明](TOOLS.md)。用户只要求最近若干条时，完成那个窗口即可，不必把请求扩大到更早历史。

“全部历史”限于所选会话在本机已经同步、可访问的记录。统一时间线没有日期下界时可从本地可用历史读取，首轮查询固定读取的时间上界；该上界不等于冻结了原数据库。分页终点、来源是否完整可读、身份是否明确、媒体是否可用，需要分别判断。超时、取消、来源故障或处理上限导致未读完时，应说明已经覆盖什么、还缺什么，不把暂时读取不到写成“没有记录”。

长历史可以分段阅读或使用导出工作流继续处理。分段是处理方式，不是缩小用户要求的理由。“读完”也需要说明读完的是指定日期范围、最近窗口，还是本机可读历史。

## 媒体和分析的表达

阅读结果应保留平台、发送者、时间和消息类型。图片 OCR 文字不等于已看懂画面；需要看图时使用实际预览。动态表情的预览目前只显示首帧，不能据此声称看完了整段动画。语音自动转写需要标明自动识别，缺失音频或转写失败不能用猜测填补。

QQ 的语音、视频等媒体尚不具备与微信相同的完整处理能力。媒体路径或消息占位存在，也不代表内容已经可读取。当前具体能力与返回状态以 [工具说明](TOOLS.md) 为准。

统计先依据实际记录与覆盖状态；关系、情绪和对话含义的分析应区分事实和推测。比如“已读范围里 A 发了 20 条”可以由统计支持，“A 一定在生气”不能由条数直接推出。没有读取的日期、其他会话和未同步历史不应被概括进结论。

## 验证到哪一层

[合成场景](SCENARIOS.md) 与工具回归可以验证给定参数下的路由、日期、身份、分页和失败行为。测试里人工编写的“用户原话 → 工具参数”说明了期望映射；它没有运行一个语言模型来独立理解这些原话，因此不能用测试通过来证明 LLM 自然语言路由已经通过验收。

客户端模型能否正确理解一句话，需要在该客户端单独观察实际选择的工具和参数。真实读取还取决于本机读取器、配置和同步范围；公开测试和文档不需要放入真实私聊内容。
