# 按用户要求验收：聊天、媒体和群分析

这里记录可以重复运行的用户场景。所有名字、稳定 ID、聊天文字、图片和 GIF 都由测试生成；不会读取本机账号、联系人、聊天数据库，不会启动微信读取器或语音模型，也不需要联网。

测试调用真正的 `Gateway.call`，实际经过工具路由、日期处理、跨平台消息标准化、合并分页、精确消息定位、上下文和群统计。替换的是微信/QQ读取器、语音服务、OCR服务这几个外部边界；图片完整解码及预览仍使用真实 Pillow。

这能检查**用户要求有没有正确转换成数据范围、返回有没有丢失或混淆、失败有没有被误报成成功**。它不证明某个实际微信版本兼容，不验证语音逐字准确率，也不代替真实 MCP 客户端的并发验收。

## 运行方法

在已安装项目依赖的 Python 环境中，从仓库根目录执行：

```powershell
python -m unittest unified_mcp.test_scenarios -v
```

测试文件为 `unified_mcp/test_scenarios.py`，合成数据为 `unified_mcp/scenario_support.py`。一项测试失败时，不应把该项需求宣传成已经通过；不能通过删掉边界断言来追求测试数量。

要查看实际的“用户原话→工具参数→工具结果”，可生成11段合成演示：

```powershell
python -m unified_mcp.scenario_support --output synthetic-scenarios.json
```

输出文件必须尚不存在。报告不含图片base64，也把临时媒体路径替换为 `<synthetic-media>`；因此报告中的媒体路径用于说明，不能当作可再次打开的真实文件。

首次在修改前版本运行的前 39 项，22 项通过、17 项失败。失败分别涉及新工具尚未接入、日期简写/发送者/类型过滤、游标条件、OCR失败时看图、GIF结果标注与 GBK管道输出。后续新增 S40—S42 防止不推进的分页和精确读取扩大用户指定范围。最终通过数量以当前执行结果为准。

本轮最终执行时，这份用户场景套件共50项全部通过。另有 `test_voice_concurrency.py` 的11项并发验收：同一音频从两个路径请求只做一个任务；取消其中一个等待者不影响另一个；最后一个等待者离开才取消任务；独立音频任务和等待者数量有上限；队列里的音频被替换时明确要求重试；后台结果的音频摘要不匹配时不传播文字；失败可重试；关闭能回收任务；状态查询不加载模型或暴露路径。它们使用固定合成识别结果，不能据此推导真实模型峰值内存。

## 用户会怎样说，工具应怎样做

### “看看我和 Alex 的聊天”

先调用 `unified_resolve_chat` 找候选。合成场景中有两个微信联系人都叫 Alex，还有一个 QQ联系人叫 Alex。返回候选后，应使用已核实的稳定 ID；昵称相同不证明两边属于同一人。

在这个案例里，使用 `wxid_synthetic_alex` 后只能出现该联系人的消息。另一个同名联系人的“different person secret”不得出现在结果里。自然语言摘要也不能绕过这个身份边界。

### “把 2026年1月2日那天从头到尾看完”

```json
{
  "tool": "unified_timeline",
  "arguments": {
    "wechat_chat": "wxid_synthetic_alex",
    "date": "2026-01-02",
    "order": "asc",
    "limit": 2,
    "include_media": false
  }
}
```

这一天按北京时间计算。合成数据的当天应有10条本地记录：包含00:00:00和23:59:59，排除前一天23:59:59与次日00:00:00。每次继续传回 `next_cursor`，直到 `has_more=false` 才能说范围内读完。

日期简写与 `after`/`before` 互斥。需要精确时区时，可以使用ISO时间；例如UTC的前一天16:00到当天16:00，应选中同一个北京时间自然日。

### “微信和 QQ 都看，全部历史都看”

确认两个平台的身份后，使用 `unified_timeline` 的两个稳定 ID，保留独立来源标签，逐页读取。合成数据中全历史为17条记录。倒序、正序都必须得到17条，且17个本地记录身份各不相同。

微信有一条普通消息和一条系统记录共用服务器 ID，必须保留两条。多个平台同一秒发送的消息也不得丢失。返回的覆盖说明仍限本机已同步历史；这个终点不证明服务器上已经没有更多未同步记录。

如果 QQ打不开，应说明合并未完成，保留微信已读页的证据，停止推进合并游标。用户明确改成只看微信后，可以独立完成微信读取。

### “找一下截止日期那句话，再看看前后聊了什么”

先使用 `unified_search` 限定目标会话和关键词。命中后，把该条的 `record_id` 交给 `unified_context`，指定前后条数。上下文必须仍来自同一会话，保持原顺序，不能使用“前后几秒”代替“前后几条”而遗漏同秒消息。

合成数据中目标服务器 ID为3；要求前1条、后3条时，目标前面应为本地记录2，后面应为4、40、5。本地记录4和40都与目标同秒，不能跳过。

### “只看这条语音说了什么”

先按明确的消息身份取回目标语音，开启媒体处理。已成功转写的语音返回文字、自动识别标识和可用音频信息；未缓存时由本地语音服务按实际配置处理。

验收中的文字是预设的合成缓存“Bring the blue folder tomorrow”，只验证单条路由及结果保存，不代表模型识别了真实音频。缺失音频的另一条语音明确返回 `unavailable`，不得把“语音消息”占位或猜测内容充当转写。

常规文字回查可以关闭媒体处理；此时不能顺便加载识别模型或进行OCR。

### “看看这张图片；这不是文字图，你直接看图”

`unified_read_image` 分别报告图片可读性、OCR状态和预览。图片能完整解码时，即使OCR不可用，也应返回预览；OCR没认出文字不能等同于图片打不开。

损坏 JPG即使扩展名和文件头正常，也不得提供“已读图片”假象。图片预览交给客户端的视觉模型后，内容分析仍应依据真实画面，不依据文件名猜测。

### “这个表情包是什么意思”

先找这条消息对应的表情实体，再调用图片预览。GIF必须保留原文件路径，说明预览只展示首帧。只看到首帧时，不能声称已经理解整段动画；动画中的完整含义需要继续查看原GIF。

表情含义还依赖上下文。可以围绕消息调用 `unified_context`，区分“画面里有什么”和“在这段对话里可能表达什么”，后者属于推测。

### “分析一下这个群，谁说得最多，都在聊什么”

先使用稳定群 ID和日期范围，调用 `unified_group_stats` 获得计数、按成员/日期/类型分布及完整性。成员按稳定 ID计数，不能按昵称合并。

合成微信群共有5条记录：成员A 2条、成员B 1条、自己1条、未知发送者1条；消息类型为4条文字、1条系统记录。两个成员显示名都叫Alex，但必须分别计算。未知发送者不能自动算到“我”名下。

如果只允许扫描2条，应明确返回局部统计 `partial`，不能把它称为整个群的活跃度。讨论主题需继续按时间线或关键词读取证据；群统计不输出好感度、情绪诊断、谁与谁关系好等无依据结论。

## 自动验收矩阵

每个编号对应 `test_sNN_*`，便于从用户要求追到执行结果。

| 编号 | 用户意图或遇到的情况 | 必须成立的结果 |
|---|---|---|
| S01 | 按同名联系人找聊天 | 返回候选，不自动合并跨平台身份 |
| S02 | 只看指定一个人 | 不混进同名联系人消息；传给微信稳定talker |
| S03 | 看某个自然日 | 含当天首尾秒，排除相邻日期 |
| S04 | 使用UTC范围描述同一天 | 与北京时间日期范围一致 |
| S05 | 双平台全部历史，正序 | 分页到明确终点，17条不重不漏 |
| S06 | 双平台全部历史，倒序 | 数量与正序相同，时间降序 |
| S07 | 多条同秒且共享服务器ID | 保留本地记录3、4、40的原顺序 |
| S08 | 两个平台找同一关键词 | 命中仍保留各自平台 |
| S09 | 空关键词搜索 | 读取前拒绝，不做全库误搜 |
| S10 | 该会话当天确实没有记录 | 成功空结果与读取失败明确不同 |
| S11 | 会话根本不存在 | 不返回伪装成功的空列表 |
| S12 | 合并时一个平台故障 | `partial`且合并游标不推进 |
| S13 | 明确只读仍可用的平台 | 不被另一平台的故障拖住 |
| S14 | 把游标用于另一个人 | 读取前拒绝 |
| S15 | 某条记录没有发送者信息 | 保留未知，不推断为自己 |
| S16 | 读取QQ群 | 传入group类型，保留不同成员ID |
| S17 | 查看指定已缓存语音 | 只有目标消息及带自动标识的文字 |
| S18 | 指定语音本地缺失 | 明确缺失，不生成假转写 |
| S19 | 图片可读但OCR不可用 | 图片预览仍返回 |

| S26 | 按消息ID看一条 | 只返回指定会话的准确记录 |
| S27 | 消息ID对应多条本地记录 | 返回歧义候选，不随便选第一条 |
| S28 | 改用本地record_id | 能区分共用服务器ID的记录 |
| S29 | 某条消息不存在 | 扫描完成后才能返回not_found |
| S30 | 扫描达到上限仍未找到 | 返回partial，不能声称不存在 |
| S31 | 看命中消息的前后几条 | 同秒消息不遗漏，上下文仍限本会话 |
| S32 | 统计同名成员的群发言 | 按稳定ID统计并单列未知发送者 |
| S33 | 只统计了群里的前几条 | 局部统计明确标记partial |
| S34 | 直接给date简写 | 与显式日期范围一致 |
| S35 | 同时给date与冲突时间范围 | 读取前拒绝 |

| S37 | 只找语音 | 不夹入文字、图片、表情 |

## 另行验收的范围

便携导出还执行了一次真实浏览器验收：5条合成记录（PNG、0.4秒WAV、两帧GIF、含emoji文字、缺失图片）以每片2条生成3个HTML分片，再把整个包复制到另一目录，使用Chromium离线模式打开。三个分片均成功加载；两张图片解码正常，WAV的 `readyState=4`、时长0.4秒且无媒体错误；类型筛选和语音转写搜索成功；缺失项与当前分片搜索范围均明确显示。没有JavaScript异常，也没有原目录或网络请求。已检查目录页和第一分片截图，未见布局溢出。这项不包含视频浏览器播放或实际语音识别。

“关闭先启动的客户端，另一个继续用”还单独用真正的 Windows MCP SDK stdio客户端验收：A创建后台，B连接同一个进程，A的桥进程及其Windows Job句柄完全退出后，B必须仍能调用同一后台。该过程曾实际发现后台随A的Job关闭而退出的问题，修复后已加入 `test_shared_service.WindowsCreatorLifecycleTests`。它使用合成Gateway，不把真实聊天内容加入公开测试。只验证TCP会话断开，无法代替这个进程退出场景。

断点恢复、缓存冲突、QQ数据库分页以及共享后台由相应模块的集成测试覆盖，不能用这里的模拟读取替代。实际启用前还应检查：

- 本机当前微信、QQ版本和已同步时间范围是否与预期一致。
- Codex与Claude分别连接时工具是否正确发现；其中一个取消或断开时另一个是否仍可查询。
- 新语音的冷启动、识别耗时、内存峰值与退出后的占用；此处的固定缓存不会测到这些指标。
- 真实识别样本是否需要人工核对，媒体是否仅有缩略图、封面或首帧。
- 导出包整体搬到其他目录后，图片、音频与视频是否仍能离线打开。

实际私聊正文不放入公共测试、演示文档或Git仓库。公开报告可以记录覆盖范围、成功/失败状态、计数和耗时，不应为了演示功能附带真实聊天内容。
