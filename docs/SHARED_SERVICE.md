# 多客户端共享后台

在客户端启动参数中使用 `--shared` 后，Codex、Claude 等客户端仍通过标准输入输出连接 MCP。前台进程只转发协议消息；相同代码、Python 环境和账号配置会连接同一个本机后台。

```text
python -X utf8 -m unified_mcp.server --shared
```

直接模式仍可用于排障。共享模式会保留各客户端自己的轻量 stdio 进程，**并不会把进程列表减少为只有一个进程**；合并的是持有微信读取器、QQ执行线程、图片识别器和语音服务的 Gateway。

## 生命周期

后台只创建一个 Gateway，由 ASGI 进程生命周期负责关闭。每个 MCP HTTP 会话独立，关闭一个客户端不会关闭其他客户端正在使用的 Gateway。

正常断开时桥接进程删除自己的 HTTP 会话。没有会话后默认空闲 120 秒退出，可用 `WXQQ_SHARED_IDLE_SECONDS` 调整（最低 5 秒）。异常退出未删除的闲置会话由 SDK 清理，最长可能多保留约 180 秒；仍有有效会话的后台不会因空闲定时器退出。

HTTP 连接建立最多等待 5 秒，收到客户端初始化请求后最多等待 20 秒握手。已建立的 SSE 连接没有读取空闲超时，避免客户端长时间未操作后连接自己失效。请求是否超时仍由调用客户端及具体后端的查询预算控制。

后台崩溃时，进行中的调用明确失败；**不会自动重放导出、缓存等可能有写入行为的调用**。重新连接 MCP 会检查旧实例是否存活，必要时启动新实例；新实例使用新令牌和新实例 ID。客户端需要重新提交上次未完成的请求，批处理任务可使用各自的恢复功能。

## 隔离与访问控制

- 仅监听 `127.0.0.1` 的随机端口。先绑定 socket、完成 ASGI 启动，再发布端点信息，避免“找空闲端口后重新绑定”的竞争窗口。
- 每个实例使用 256 位随机 Bearer 令牌。令牌不写入客户端配置、命令行或日志，存于私有目录的 `endpoint.json`。
- Windows 目录采用受保护 DACL，只允许当前用户 SID 和 LocalSystem；凭据、锁、日志从创建时就继承此权限。其他平台使用用户所有的 `0700` 目录及 `0600` 凭据文件。
- 连接同时检查实际对端是回环地址、Host 是精确端口、Origin 合法、Bearer 正确；不信任环境代理。健康探测不跟随重定向。
- 账号目录、模型等相关环境配置、文件配置摘要、代码摘要和 Python 路径组成实例指纹。不同配置会启动各自的后台，避免把账号或识别设置混用。摘要不会输出密钥内容。
- 启动锁保护并发启动；实例锁由后台持有整个生命周期。进程退出后 OS 自动释放锁，遗留的锁文件不会冒充活进程。

同一 Windows 用户下的恶意程序仍处在相同信任范围内。共享后台没有把 MCP 变成跨用户安全沙箱，也没有改变连接云端 AI 后返回内容可能离开本机的边界。

## 协议保留

stdio 桥接直接转发完整 MCP 消息，包括工具输入/输出 schema、图片、结构化结果、`isError`、`_meta`、初始化说明及取消通知，不将返回值重新压成一段文本。

使用当前固定的 MCP SDK 1.30 Streamable HTTP 实现。服务端使用 SSE 响应模式，以避免该 SDK 的 JSON 响应模式在取消进行中请求时可能产生的 HTTP 500。只接入一个 `StreamableHTTPSessionManager`；每个 SDK 会话的生命周期不拥有共享 Gateway。

## 排障

状态保存在 `WXQQ_DATA_DIR/shared-service/<配置指纹>/`，默认根目录为当前用户本地应用数据中的 `wx-qq-mcp`。`daemon.log` 也受相同权限保护。不要将 `endpoint.json` 或整个状态目录上传到公开仓库。

连接时已有后台无法响应而实例锁仍被占用，会有界失败并提示查看私有日志；不会任意结束无法确认身份的进程。代码或配置改变后会使用新指纹，旧后台在其客户端断开并空闲后退出。所有客户端应使用相同安装路径、Python和配置，才能实现共享。

Windows MCP SDK 会给 stdio 客户端进程设置关闭时结束子进程的 Job Object。仅使用独立进程组仍会继承该 Job，本项目在实际 SDK 双客户端测试中复现了“A 退出后共享后台随之被结束”。因此 Windows 启动改为本机 WMI `Win32_Process.Create`，使后台不继承发起客户端的 Job；微软在 [Job Objects 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)中说明了这个区别。

短暂的 PowerShell 启动器使用 `CREATE_NO_WINDOW`；WMI 后台使用 `DETACHED_PROCESS` 和 `ShowWindow=0`，不连接父控制台。本机 WMI provider 对 `CREATE_NO_WINDOW` 返回参数错误 21，而文档列出的 `DETACHED_PROCESS` 已通过实际启动验证，所以不能只照搬 `CreateProcess` 的标志。[WMI 启动配置](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processstartup)

完整环境通过同一私有 ACL 目录下的一次性 bootstrap JSON 传递，命令行只带 bootstrap 文件路径。后台先恢复环境、重定向到私有日志并删除 handoff，再导入服务，避免模型、账号或缓存配置丢失。WMI 创建失败会报告安全的状态码或异常类型，不回退到已知会继承 Job 的启动方式，也不会输出环境值。WMI 服务或命名空间被系统策略禁用时，共享模式会明确失败；管理员需恢复本机 WMI 权限，或在独立终端预启动后台。

## 本次验证范围

自动测试使用合成 Gateway，通过真实 loopback HTTP/MCP 验证两客户端共用一实例、关闭或取消其中一个不影响另一个、完整消息桥接、访问控制和私有目录权限。另有实际后台子进程的并发启动、强制中断后恢复、凭据轮换和空闲退出测试。这些验证不读取真实聊天，也不等于已经证明所有客户端版本的长期运行稳定性。
